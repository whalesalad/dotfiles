## Per-client tmux scrolling on Lucifer

The original host override selected scroll behavior from the host running the
tmux server. That was insufficient for a tmux session on Lucifer driven over
SSH from Viper: the physical mouse and its high-resolution event stream belong
to Viper, but tmux loaded Lucifer's three-line binding.

Lucifer's copy-mode wheel bindings now classify the tmux client that generated
each event by checking `/proc/#{client_pid}/environ` for `SSH_CONNECTION`:

- SSH-attached clients scroll one line per event.
- Clients local to Lucifer scroll three lines per event.

Using `#{client_pid}` keeps the choice per client, including when local and SSH
clients are attached to the same tmux server simultaneously. This assumes all
SSH clients should receive the Viper-style behavior.

Validation and observations:

- Loaded `tmux/hosts/lucifer.conf` into an isolated tmux 3.7b server and
  inspected both `copy-mode` and `copy-mode-vi` bindings successfully.
- `git diff --check` passed before the change was committed.
- A local benchmark of 1,000 `/proc` checks using `grep -zq` took 2.14 seconds
  on Viper. The per-event subprocess cost may become noticeable with a
  high-resolution wheel.
- Confirmed in real use that SSH-driven scrolling works and has not shown a
  latency problem so far.
- Recorded in commit `69bd696` (`experimenting with different scroll
  characteristics over ssh`).

If latency becomes noticeable, the next approach is to classify each tmux
client once when it attaches and cache that classification instead of spawning
a shell and `grep` for every wheel event.
